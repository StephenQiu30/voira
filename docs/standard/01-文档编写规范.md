# 01 文档编写规范

## 01 入库标准

知识库只保存长期有用的需求、设计、接口契约、验收标准及有来源的决策结论。草案可以入库，但必须明确哪些已确认、哪些待评审；工作过程不能以“草案”名义长期堆积。

不入库：逐轮交付日记、生成／抓取记录、OCR、工具回包、临时排障、候选提示词、重复状态表、旧稿全集、空白模板。过程输出放被忽略的output或系统临时目录；必要恢复副本放被忽略的.local。真实运行Skill、配置和已采用素材属于工程事实源，不当作过程文件删除。

## 02 唯一归属与最小结构

| 位置 | 维护内容 | 最小写法 |
|---|---|---|
| requirement | 一功能一文档、唯一主FR；01只作范围／NFR／Q索引 | 问题和来源 → 边界 → 功能规则 → 确认及剩余问题 → 验收关联 |
| design | 现行设计、取舍、流程、状态、异常 | 需求映射 → 设计规则 → 必要契约及数据 → 例外／验收入口 |
| prd | 用户故事与可测试AC | 用户价值 → 故事 → 给定／当／则 → 发布边界 |
| plan | 尚需实施的依赖、任务与稳定测试场景 | 基线与准入 → 依赖／交付 → 追溯 → 验收／回退 |
| research | 会改变方案选择的研究结论 | 问题 → 带日期／版本的来源 → 已知事实 → 取舍及限制 |
| standard | 编写、目录、前端与后端规范 | 按实际需要使用本表；目录位置见[文档目录规范](02-文档目录规范.md)，不另建空白模板 |

共享HTTP／状态／数据契约集中在design02；功能特有规则可按DES编号合并为章节，不要求一功能一设计文件。人设故事归design05，外观规则归design04，运行提示词归backend Skill及配置，避免多份复制。工程结构归PROJECT，通用视觉归DESIGN，页面交互归design01/06。design目录只放Markdown设计文档，不存放样式、令牌或素材文件。

## 03 编号、状态与来源

- 同一目录内的文档从00或01起使用连续两位编号和中文名称。合并或删除后重排空号，并同步标题、链接与简称。根目录及两端README／AGENTS保留入口名称。
- FR/NFR、DES、US/AC、T、TC、RES编号稳定，不因文件重排而改号；已废弃的稳定ID不复用。合并时迁移到唯一所属章节。已替代条目只保留必要对照，不保存完整旧正文。
- 文档属性只需类型、状态、更新；业务状态为草案／已确认，规范和导航为有效。已确认须有用户依据，整理文档不自动升级确认状态。
- 已知事实、建议、假设与未验证项分别写明；第三方演示和静态阅读不等于本项目实测。来源尽量直接链接官方页面、固定源码提交及必要页码；不把原始抓取包塞入知识库。
- 用户新指令优先，直接更新所属正文，移除被替代表述；不再追加“本轮T-xxx修订”让读者自行判断哪段有效。秘密与带凭据链接不得入库。

## 04 追溯与验证

计划02只维护一张完整FR/NFR → DES → US/AC → T → TC追溯；其他文档保留指向所属规则的必要链接。验收必须能检查成功、失败与边界；不编造工期、规模、性能或通过成绩。

验证结论区分静态检查、Mock、浏览器、真实服务及人工评审。规范和方案保存可复用检查方法；当前验证摘要只在HANDOVER更新，原始证据留output。不得在需求、设计、计划、任务表和交接五处重复粘贴同一轮检查。

## 05 任务与交接

BLACKLOG是唯一任务状态表，采用待办／阻塞／进行中／已完成；仅保留当前队列和必要完成里程碑。HANDOVER保留当前可用能力、最近有效验证、未测项和下一步，覆盖旧状态，不追加完整历史。过去的过程通过Git历史或必要本地恢复副本追溯。

完成任务时更新相关规则、BLACKLOG及HANDOVER；只有任务／验收规格变化时才改plan。文档确认、实现完成、真实验收是不同事实。提交、推送、部署权限由AGENTS和用户授权控制。

## 06 合并与删除检查

先核对并行改动和实际事实源。合并时保留独有业务规则、确认依据、未决问题及必要编号；删除过期计划、重复报告和过程文件，修复路径及章节锚点。原始资料需要保留时移到知识库外，不重写原件；Obsidian运行配置保持原状。

交付前检查本地链接、稳定ID、追溯、现行口径和未改动的工程范围。能通过一段规则说明的内容不拆成多份文档，不为证明整理完成新增整理报告。
