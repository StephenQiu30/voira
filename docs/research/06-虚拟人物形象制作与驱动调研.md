当前决策更新：用户已确认Vidu、蓝色大肥鱼、人物与背景合成画面、提问后回答；已补充确认本地优先及PoC由本地Codex回答、协议从简，Q-010/011关闭。当前Codex生成答案后交给Vidu text_tts播读，替代早期Vidu直接生成回答的建议。下文保留当时研究建议及证据语境，五项体验选择已按用户回复确认，Q-012/013关闭；具体音色和真实效果仍未验证，预算等实际调用前再定。当前执行边界以[需求索引v0.10](../requirement/01-数字人MVP需求草案.md)及[最小业务设计](../design/03-Vidu网页PoC最小业务设计.md)为准；不再重复选择首测角色、互动模式或透明分层。

## 01 研究问题与结论

本轮回答“网页中的角色形象具体怎么准备、怎样接入、怎样判断做对了”。范围沿用[网页PoC需求](../requirement/01-数字人MVP需求草案.md)，只整理资料与规格。直播、换装、声音克隆、素材管理后台和多角色同时运行均不进入本轮。

**建议先从现有视觉候选中选一个角色，形成一张干净送模底图、一个系统音色、一份简短人设，再用真实网页验证它能否稳定说话。** 参考仓库可以借鉴资产组织和会话输入方式，但没有公开作者实际使用的角色资产。抖音教程提供离线制作方法，不提供本项目的实时效果证明。

本地并行设计已发生更新：[DESIGN第15节](../../DESIGN.md#15-五位角色与手机交互细化2026-10-25)记录蓝色大肥鱼、Gemini、Claude、Grok、ChatGPT五位角色的视觉映射，当前首页不再采用早期真人“小伴”。这些是角色称呼/设计映射，不代表接入相应大模型。本研究尊重该方向，不据教程重新决定性别、换回真人或增加第六个角色；具体首测角色仍在需求Q-004落实。

现有[五位角色素材记录](../design/02-五位角色素材生成记录.md)已保存逐角色提示词和文件位置。当前Figma默认展示蓝色大肥鱼，建议真实首测也优先沿用它以减少变量；最终送模版本和动态效果仍需评审，不将首页默认展示推定为真实服务已选定或已接入。

### 02.1 采集限制

Firecrawl直接读取两条教程时分别停在“视频数据加载中”和“服务器出现问题/登录入口”；HTTP 200未被当作内容成功。随后REA临时Chrome访问公开页面，取得作者、实际发布日期和章节要点。第二页Firecrawl返回的通用当天标题没有用作教程发布日期。搜索索引可能滞后，章节/智能文稿也可能存在识别错误。

两次REA均只采集URL、可访问性树及有限网络事件，未收集请求体、响应体和头值，未点击登录或授权设备。各保留400条事件、分别遗漏768/716条，完整性为incomplete；因此不据此推断抖音后端、视频生成接口或实时协议。两次浏览器均由工具终止清理。归档额外移除了URL查询值，原Evidence ID和工具原始摘要保留为来源标识，不能拿归档后的文字反算原摘要。

## 03 仓库拆解：角色如何进入实时会话

固定源码的流程为：角色配置引用图片和人设 → 读取图片字节并上传资产 → 组合avatar/persona/voice/开场指令 → 创建Vidu会话 → 网页接收媒体。源码本身不训练人物模型，也不包含本地数字人权重。[session.py](https://github.com/garycaogan/ai-live-avatar/blob/5559ec5440c93814737155183dbe832df0b9f215/live/session.py#L457-L508)

| 拆解项 | 源码或作者实际内容 | 对本项目的取舍 |
|---|---|---|
| 角色资产 | 作者实际照片、人设、音色与录屏未公开；示例配置的xiaoshen.jpg在固定树中不存在 | 自有候选需单独制作、选择和验证；不能下载仓库就复刻原角色 |
| 底图 | 作者建议单人近景、自然表情，底图同时决定衣服和房间 | 保留单一身份、清晰面部和稳定构图；当前二次元画风不强制改成作者的写实提示词 |
| 比例 | README的1.2:1服务于抖音上半屏布局 | 不作为网页比例或Vidu硬约束 |

| 音色 | 系统音色与私有克隆音色并存；克隆另需样本、处理和上传 | 首测建议一个系统音色，声音克隆后置 |

| 教程 | 公开内容中的制作链路 | 本项目采用的部分 | 不直接迁移的部分 |
|---|---|---|---|

## 05 当前形象路线与供应商输入边界

### 05.1 三类图不能混用

| 资产 | 用途 | 当前建议 |
|---|---|---|
| 角色母版/透明立绘 | 保留原始形象，供设计裁切和背景分层 | 沿用当前五位候选；保留原文件，不覆盖生成来源或把UI烘焙进图 |
| 网页封面/头像/场景预览 | 未开始、加载及Figma视觉评审 | 按现有布局裁切；必须明确是静态预览，不能冒充实时反馈 |
| 送模派生图 | 被供应商用来生成该角色 | 先用一个角色与固定背景合成一张干净完整图，单独版本化；透明立绘不是已确认的实时透明视频输入/输出协议 |

当前两张抽查立绘有清晰嘴部，但属于较远的坐姿全身构图，发饰、衣饰细节较多。**建议**首测另做同一角色的胸腰以上构图，保留发色、瞳色、发型和关键服饰，减少面部在画面中占比过小的问题；这只是待评审的派生图方案，不修改既有立绘。若裁切破坏用户指定造型，应保留原图并比较构图，不先替换身份。

网页可以在静态阶段分层摆放PNG与背景，但供应商返回视频是否带透明通道未验证。真实视频若不透明，需把角色和背景作为同一画面适配，不能承诺网页背景可独立实时替换，也不默认增加抠像方案。

### 05.2 官方约束与项目建议分开

[Vidu图片上传文档](https://platform.vidu.cn/vidu-stream/doc/image-upload)描述：一张单人图，支持全身/半身与多种风格；格式PNG/JPG/JPEG/WEBP；图片大小≤50MB，base64解码后字节长度<20M并带内容类型前缀。资产有created、processing、success、failed状态，文档说明图片90天后自动删除。资产上传就绪不等于动态效果通过，长期可复现仍应保存本地母版与映射。

本次读取的上传页未列像素尺寸或纵横比门槛；不推定其他会话端没有限制。源码的HEIC接收和1280/2048处理参数不能覆盖官方格式说明。母版尺寸保留原样，派生图按实际接口测试；没有必要先臆定4K输出或补一套3D建模流程。

音色列表按实时版provider和非实时版分组。**建议**先按实际选择的实时接口/provider/国内外环境筛出2—3个候选，用同一段中文试听后只选一个；网页角色名与voice ID分开记录。没有试听就只标“候选”，不依据音色名称宣称和人物匹配。

### 05.3 方案取舍

当前首选研究路径是“现有二次元角色 → 单张合成底图 → Vidu候选服务 → 网页动态评审”。它复用已有源码证据、无需先建Live2D/3D模型，但身份保持、口型、服饰稳定和不透明媒体布局仍是风险项。

若该角色在真实短测中明显变脸、改变画风或反复破坏关键造型，先检查构图并只改一个因素复测；仍不合格则记录证据，回到Q-004决定换首测候选或另研究受控2D/3D驱动。后者是后续技术决策，不在本轮默认新增绑定、骨骼、动作库或双渲染管线。

## 06 建议制作流程与交付包

业务约束在[需求第09节](../requirement/01-数字人MVP需求草案.md#09-虚拟人物形象与素材要求)维护，本节仅描述实现该素材规格的方法。本轮没有制作或替换图像。

1. **选首测角色**：从现有五位候选中选一个，记录显示名、角色标识、原图路径和固定特征。其他候选保留在设计资产集合，不要求同时接入。
2. **形成角色说明卡**：写明画风、发色/瞳色/脸型、服装与配饰、表情、背景、声音方向、简短性格。颜色与造型以选定原图为准，不凭角色名称编造人格或模型能力。
3. **准备干净底图**：保留母版；制作一个面部/嘴部清晰、无UI/水印/其他人物、固定背景的送模派生图。静态页面预览可另做裁切，但不能覆盖送模图。
4. **静态评审**：检查身份、眼睛/嘴/手、关键装饰、裁切和前景遮挡；对照桌面实际媒体区。手机稿另作设计参考，不升格成当前PoC多端验收条件。
5. **选择音色和人设**：限定在目标实时服务可用音色中试听，记录一个voice ID/provider；人设写身份/语气/能力范围，开场意图单独维护。首测不复制直播话术，不要求克隆。
6. **真实短测**：账号预算与网页链路条件落实后，按TC-016/017/020评审同一底图、同一音色的待机、短句、长句和连续回应；实际说出的内容与观测记录对应。
7. **冻结可复现版本**：只改一个因素再比较。保留母版、送模图哈希、角色/人设版本、供应商配置与失败记录；真实动态不通过时不得只凭静态图宣布角色可用。

建议交付包为：角色说明卡、母版与送模图、网页预览裁切说明、来源/使用范围记录、音色选择记录、人设与开场意图、动态评审记录。可用文件和配置完成，不建设素材CMS或生产流水线。本轮不预创建空资产目录或应用脚本。

用于后续制作派生图的提示词结构（**本项目建议，未执行且不保证效果**）：

> 以已选角色母版保持同一身份与二次元画风，保留指定发色、瞳色、发型、服装和关键配饰。单人，胸腰以上构图，目光接近镜头，自然放松表情，眼睛和嘴清晰无遮挡；固定机位与背景，光线方向一致，预留界面裁切空间。不要出现其他人物、文字、Logo、按钮、水印，不新增配饰，不改变角色造型。

人设示例仅表达规则，显示名待选定后替换：你是声伴网页中的AI虚拟角色；用自然、简短的中文回应当前文字，语气友好；不了解的信息说明不确定；只描述网页已有能力，不承诺换装、唱跳、长期记忆或接管外部设备。测试台词单独放评审记录，不作为人设里的固定示范回答。

## 07 验证样本与需求影响

下面是建议样本类型，不是已执行成绩，也不增加已确认的测试费用。按Q-005确认后的约10条额度组合，模式只按Q-004选一种。

| 样本 | 建议观察 | 映射 |
|---|---|---|
| 待机→首句→结束 | 是否保持原角色；开始发声时嘴有对应变化；无黑屏/冻结/无声 | FR-001/011，TC-016 |
| 简短自我介绍 | 面部、嘴部、音色与角色是否协调；AI身份是否清楚 | NFR-002/004，TC-017 |
| 由短句组成的较长回答 | 眼睛/嘴/牙齿异常，发饰、服饰与背景是否漂移 | NFR-002，TC-017/020 |
| 含数字、日期和中英文名称 | 实际发音是否可理解，停顿是否自然；不把台词发送成功当作口型通过 | NFR-002，TC-017 |
| 连续数次不同输入 | 同一人、同一音色，未重复旧回应；固定装饰没有累积变形 | FR-005，NFR-002/007，TC-020 |
| 静音/恢复、结束 | 不用无声或循环待机掩盖错误；保留结束核对 | FR-006/007，TC-018/019 |

回答模式记录“用户输入+实际回复”；不能要求模型逐字读回问题。播读模式记录“指定台词+实际输出”；没有该模式能力时不伪造通过。口型与声音的定量偏差本轮不设未经实测的阈值，先留真实样例及问题时间点，再由Q-004落实观感接受程度。

静态检查与动态验收分别记录。已存在图片、alpha通道、Figma图层或资产API的success，均不能替代FR-011的真实网页链路。

### 09.2 推荐理由与选择条件

**分析建议：优先用Vidu实时版验证网页单角色闭环；Live2D作为透明分层/保形要求更高时的条件备选。** 前者已有输入、控制、RTC的参考代码，省去本轮制作绑定模型的步骤；这只是当前资料和资产条件下的工作量判断，不代表速度、价格或质量已获证明。

现有五位角色及A/B坐姿是静态美术方向。若首轮真实动态也必须独立分层、严格保持复杂服装与配饰，则需要先解决需求Q-011，不能因为当前推荐Vidu就要求修改既有视觉目标，也不能声称PNG的alpha会自然保留在云端视频里。

Live2D路线需要先完成可驱动模型，再将真实回复语音接到嘴部参数和网页播放时序；3D/VRM需要另一类资产；自托管唇形模型需要推理与媒体工程。三者都不能靠导入当前PNG直接获得完整交互。当前不并行建设多套渲染系统，也不把工程方案建议视为用户已批准的费用或实现任务。
